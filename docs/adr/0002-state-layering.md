# 状态按生命周期分层：持久化应用 store、全局界面 store、页面局部状态

Zustand 官方推荐单一 store，大型应用再按 slices 拆分。但 `persist` 中间件是按 store 工作的：一个 store 只写一个存储键，而且每次 `set` 都会把 partialize 后的全部状态重新序列化写入，不管这次改动的是不是要持久化的字段。localStorage 是同步存储，写入失败时异常会从 `set` 直接抛给调用它的 action。

如果所有状态都放进同一个持久化 store，在筛选框里每输入一个字符，就会把整个工作区重写一遍；存储写满后，切换 Tab 这类纯界面操作也会抛异常。partialize 还得小心排除 Tab 和筛选条件，否则用户下次打开会看到上次的 Tab 和筛选。DevTools 的时间线也会被无关的界面操作淹没。

因此我们按生命周期和共享范围分层：

- **持久化应用 store**：工作区、本机设置、Gist 设置、主题。挂 `persist`，只写一个存储键。
- **非持久化全局界面 store**：存储状态、跨页面共用的当前选中 Agent。不挂 `persist`。
- **页面局部状态**：页面内的 Tab、筛选条件、表单，用 `useState`。（筛选条件已改为放进 URL 查询串，见 ADR 0003。）
- **跨页面的一次性意图**，比如从标签页带着标签筛选跳到工具页，通过 `history.state` 传递。wouter 的 hash 路由会把 URL 查询参数写进 `#` 前面的查询串，之后切换页面时不会清掉，所以不用查询参数。（已被 ADR 0003 取代：列表筛选条件放进 URL 查询串。）

“单一 store”作为“避免多个 store 互相依赖”的原则仍然成立，两个 store 之间只有一个方向的依赖：应用 store 更新界面 store 中的存储状态，界面 store 不读写应用 store。具体是持久化把读写错误和启动时的回退原因写进界面 store，设置被重新填写时清除对应的回退提示。

## Considered Options

- **严格单一 store，用 partialize 排除界面状态**：符合官方推荐，但有上面列出的写入放大和异常扩散问题。
- **按领域拆成多个持久化 store，各挂一个 `persist`**：工作区、本机设置、Gist 设置可以各自保留独立的键，但 store 数量多，彼此之间的读取依赖分散。
- **按生命周期分两个 store 加页面局部状态（采用）**。

## Consequences

- localStorage 中只有一个键，Gist Token、Gist ID 和本机设置与工作区存放在一起。导出文件和 Gist 推送只序列化工作区，由单元测试守住这条隐私边界。
- 存储状态放在界面 store 中，所以记录写入错误本身不会再次触发持久化写入、造成循环。
