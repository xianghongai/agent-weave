# 预设是按 Agent 拆分的 JSONC 数据文件，构建时合成一份工作区

预设原来是 `src/lib/` 下的 TypeScript：ID 由函数拼出，整体允许的规则由“命令清单减去例外”推导，取舍理由只写在代码注释里。维护预设要读懂代码，社区也无法只改一个 Agent。我们改为在仓库根目录的 `presets/` 下手写 JSONC：每个文件都是一份部分工作区，顶层键与导出文件相同，每个 Agent 一个文件；构建时把它们合成一份工作区随站点打包，同步、导出、导入仍然只用一个文件。

## Decision

- 文件中的条目结构与导出文件一致，规则全部逐条写明，不再由代码推导。
- Agent 文件可以带只属于预设的 `priority`，合成时按它降序、同值按文件名排序后丢弃，不进入工作区。
- 预设中给人看的文字写成键，各语言的文字放在 `presets/locales/` 下的语言文件中，合成时替换；进入工作区后就是普通数据。按界面语言合成的方式见 ADR 0005。
- 语法错误中断构建；结构、引用、文案键等逻辑问题在构建时只警告，由单元测试失败在 CI 中拦截，部署前也跑测试。
- 导入导出与 Gist 统一使用 JSONC（`jsonc-parser`），导出内容仍是格式化的纯 JSON。

## Considered Options

- **TypeScript 源码**：可以复用函数、写注释，但维护数据要读代码。
- **单个 JSON，在站点中编辑后导出覆盖**：站点即编辑器，但不能写注释，所有 Agent 挤在一个文件里，协作容易冲突。
- **按 Agent 拆分的 JSONC（采用）**：手写维护，取舍理由写进描述或注释，下线、改名一个 Agent 只动一个文件。

## Consequences

- 新增一个命令工具，要同时补它的规则和文案；测试会检查没有规则、又不在豁免名单中的命令。
- 构建不会因逻辑问题中断，坏预设只能靠 CI 拦住：每位新用户都从预设起步，悬空引用会让刷新后的本地数据校验失败并回退。
