# 预设改为数据文件，并按调研确定主流 Agent

Status: ready-for-agent

## 问题陈述

预设是随站点发布的初始工作区内容，每位新用户都从它起步。现在它写成 TypeScript 源码：ID 由函数拼出，约 170 条整体允许的命令规则由“命令清单减去例外”推导，MCP Server 的允许规则和 Antigravity 的写目录规则也是代码展开的，取舍理由只写在代码注释里。维护预设要先读懂代码，社区贡献者无法只改一个 Agent；某个 Agent 下线或改名，要改动多处源码。

预设收录的 Agent 也只有 Claude Code、Antigravity 和 Codex CLI 三个。同批调研（权限、MCP、内置工具三份）已经梳理了主流 Agent 的格式，其中不少能用现有的 Agent 定义表达，却没有进入预设。

另外，工作区文件、Gist 都只接受严格的 JSON；权限规则没有描述，用户看不到某条规则为什么存在。

## 解决方案

分两个阶段，写在同一份 spec 中：

- **阶段一：迁移机制**。预设改为手写的 JSONC 数据文件，放在仓库根目录的 `presets/` 下：标签、命令工具、MCP Server、共享规则各一个文件，每个 Agent 一个文件。构建时合成一份工作区随站点打包，同步、导出、导入仍然只用一个文件。预设中给人看的文字写成键，中文放在预设自己的语言文件中。导入、导出与 Gist 统一使用 JSONC。权限规则增加可以为空的描述。
- **阶段二：按调研确定内容**。按三份调研确定收录哪些 Agent，以及每个 Agent 的权限输出、MCP 输出和内置工具，同时补全有理由的规则描述，并更新 Agent 格式文档。

决策依据见 ADR 0004。

## 用户故事

### 预设维护者与社区贡献者

1. 作为预设维护者，我希望预设是数据文件而不是源码，这样修改预设不需要读懂 TypeScript。
2. 作为预设维护者，我希望预设文件的条目结构与导出文件一致，这样我只需要理解一种格式。
3. 作为预设维护者，我希望预设文件允许注释和尾随逗号，这样手写时不容易出错，也能就地写明细节。
4. 作为社区贡献者，我希望每个 Agent 是一个独立文件，这样新增、下线或改名一个 Agent 只需要动一个文件。
5. 作为社区贡献者，我希望标签、命令工具、MCP Server、共享规则各自一个文件，这样我能快速找到要改的地方，多人同时修改时也不容易冲突。
6. 作为社区贡献者，我希望每一条规则都在文件里逐条写明，这样我看到的就是站点实际使用的规则，不需要推算。
7. 作为社区贡献者，我希望 Agent 文件可以声明优先级，这样主流 Agent 能排在前面，而新增 Agent 时不需要维护一份清单文件。
8. 作为社区贡献者，我希望优先级相同的 Agent 按文件名排序，这样顺序可以预期。
9. 作为社区贡献者，我希望预设中给人看的文字都集中在预设的语言文件中，这样文案可以统一校对，将来也能翻译。
10. 作为社区贡献者，我希望 `presets/` 下有一份 README 说明原则和方法（文件结构、ID 取名、优先级、文案键、新增命令时要补规则），这样我第一次贡献就知道怎么做。
11. 作为社区贡献者，我希望“为什么不收录某个命令或 Agent”这类细节写在相关文件的注释或描述里，而不是写进 README，这样细节和数据放在一起，README 也不会过时。
12. 作为社区贡献者，我希望 JSONC 语法错误会中断构建，并报出文件名和行列，这样我能立刻定位问题。
13. 作为社区贡献者，我希望悬空引用、重复 ID、重复标识、缺少文案键这类逻辑问题在构建时给出警告，带上出问题的条目 ID，但不打断本地开发。
14. 作为社区贡献者，我希望这些逻辑问题会让单元测试失败，这样有问题的预设无法通过 CI 合并。
15. 作为社区贡献者，我希望新增一个命令工具却忘了给它写规则时，测试会提醒我，除非它在测试列出的“故意不写规则”名单中。

### 阶段二：主流 Agent

29. 作为 Claude Code 用户，我希望预设的内置工具覆盖所有受权限规则控制、值得单独放行或拒绝的工具，并说明为什么不收录 `Write`、`NotebookEdit`、`Glob`。

32. 作为 Gemini CLI 用户，我希望预设至少能生成 MCP 配置，并说明为什么不生成权限。
33. 作为 Qwen Code 用户，我希望预设能生成权限和 MCP 配置。
34. 作为 Cursor CLI 用户，我希望预设能生成权限配置中它能表达的部分（没有询问这一档），表达不了的规则列为跳过的规则，并能生成 MCP 配置。
35. 作为 CodeBuddy Code 用户，我希望预设能生成权限和 MCP 配置。
36. 作为 Devin CLI 用户，我希望预设能生成权限和 MCP 配置。
37. 作为想了解支持范围的用户或贡献者，我希望能查到哪些 Agent 没有收录、卡在哪里，这样有人想补充时知道从何下手。
38. 作为预设维护者，我希望 Agent 格式文档按新的调研更新，并指向新的预设文件位置。

## 实现决策

### 预设文件与合成

- 预设目录位于仓库根目录，不放进 `src/`：它是数据，不是源码。
- 每个文件都是一份**部分工作区**，顶层键是导出文件的键（`tags`、`command_tools`、`mcp_servers`、`agents`、`rules`）中的若干个。共享规则单独一个文件；某个 Agent 内置工具的规则放在该 Agent 的文件里。
- Agent 文件可以在顶层声明 `priority`（整数，越大越靠前，省略为 0）。合成时先按优先级降序，同值按文件名升序排列 Agent，然后丢弃该字段，它不进入工作区模型。阶段二的取值：Claude Code、Codex CLI 为 100；Antigravity、Gemini CLI、Qwen Code、Cursor CLI 为 50；CodeBuddy Code、Devin CLI 省略。
- 合成把各文件中的同名数组依次拼接：先是根目录下的文件（标签、命令工具、MCP Server、共享规则，按固定顺序），然后是排好序的 Agent 文件。最后补上当前的结构版本，以及一个固定的旧修改时间。这个时间是逻辑而不是数据，留在代码中，保证用户的任何一次编辑都比它新。
- 预设中给人看的文字写成文案键，包括标签名、各条目的描述、高危说明、Agent 描述、作用域的名称和说明、规则描述。中文放在预设目录下的语言文件中，与界面文案的语言文件分开：前者是数据，后者是界面。键名以条目 ID 为前缀，如 `<条目 ID>.description`。合成时把键替换成文字；站点只有简体中文，替换在构建时完成，运行时不再涉及。
- 内部 ID 保持人类可读的 `preset-<种类>-<后缀>` 约定，“合并预设”继续按它判断条目是否已存在。
- 合成是 `src/lib/` 中的纯函数。输入是“文件路径加文本”的列表和语言文件文本，输出是合成后的工作区加一组警告；语法错误单独返回。它不依赖文件系统，读文件由调用方负责。
- 构建插件位于构建目录，只负责读取预设目录、调用合成函数，并以虚拟模块提供合成结果。语法错误让构建失败，并报出文件名和行列；逻辑问题通过 Vite 的警告输出，不中断构建。开发服务器在预设文件变化时重新合成。
- 合成后的工作区还要经过与导入相同的校验。不通过时，不通过的原因作为警告报出。缺少文案键、键没有被任何条目使用，也作为警告报出。
- 原有的预设 TypeScript 模块删除。“返回预设工作区的独立副本”这一接口保留，内部改为读取虚拟模块，合并预设、重置为预设和持久化的回退都不受影响。
- 阶段一的数据沿用现有内容，搬运时直接改写为 JSONC：推导出来的规则逐条展开，代码注释中的取舍理由改写成相关条目的描述或 JSONC 注释。不做新旧等价测试，也不保留旧实现作为对照。

### 工作区文件与 Gist

- 导入（文件和 Gist）改用 `jsonc-parser` 解析，允许注释和尾随逗号；内容无法解析时，仍然返回“无法解析”这一原因码。
- 导出文件名改为 `agent-weave-YYYY-MM-DD.jsonc`，内容仍是格式化的纯 JSON。导入框同时接受 `.json` 和 `.jsonc`。
- Gist 中的文件名改为 `agent-weave.jsonc`。项目尚未发布，不兼容旧文件名。
- 浏览器本地存储不变，仍按 JSON 读写。
- 工作区校验在返回原因码的同时，带上出问题的条目 ID（结构错误无法定位到条目时可以不带）。界面在导入失败、存储回退的提示中显示它；构建警告也使用它。

### 规则描述

- 权限规则增加 `description` 字符串字段，空字符串表示没有描述。校验要求该字段存在。不写迁移：已有的本地数据和导出文件会校验不过，按现有逻辑回退到预设，这个代价可以接受。
- 新增和修改规则的操作接受描述；“合并预设”按原样带上预设规则的描述。
- 规则对话框增加一个可选的描述输入，写法与命令工具的描述一致；规则列表的显示方式与工具列表对描述的显示方式一致，有描述才显示。字段名等界面文案放进界面的语言文件。
- 生成配置时不输出规则描述。

### CI 与部署

- 逻辑问题由单元测试拦截：真实预设合成后没有警告，并能通过导入校验。
- GitHub Pages 的部署工作流在构建前先运行单元测试，避免直接推送到 `main` 时绕过检查。

### 阶段二：内容

- 收录的 Agent 及表达能力：
  - 权限和 MCP 都输出：Claude Code、Antigravity、Qwen Code、CodeBuddy Code、Devin CLI。
  - 部分权限加 MCP：Cursor CLI。没有询问这一档，对应的决策键留空；带子命令的命令模式表达不了时，对应模板留空，规则列为跳过的规则。
  - 只输出 MCP：Codex CLI（命令规则是 Starlark，权限配置文件仍是 beta）、Gemini CLI（`tools.*` 列表有弃用项，参数只对 Shell 有效，MCP 的放行在另一个路径；主推的 TOML 策略引擎模板表达不了）。
- 不收录的产品（OpenCode、Amp、Zed、Kimi Code、Kiro、Continue、Trae、VS Code Copilot、Copilot CLI 等），在 Agent 目录中用 JSONC 注释写明原因：规则是对象或数组、正则、YAML、界面开关或命令行参数，现有的 Agent 定义表达不了（ADR 0001）。
- 内置工具只收录“受权限规则控制，并且用户有理由单独放行或拒绝”的工具。不需要审批的工具（待办、提问、工具搜索等）不收录；规则不会命中的工具（如 Claude Code 的 `Write`、`NotebookEdit`、`Glob`）不收录，并在相近工具的描述中说明。各 Agent 的工具清单以三份调研为依据，按同一标准确定。
- CodeBuddy Code 和 Devin CLI 的 MCP 配置路径调研没有写清楚，动手前先查官方文档确认；查不到可靠来源时，该 Agent 不输出 MCP，并在作用域说明或注释中写明。
- 预设规则中有特别理由的填写描述，约 170 条整体允许的规则留空。
- Agent 格式文档改为指向新的预设文件位置，调研日期更新为 2026-10-24，并补充新收录 Agent 的格式规则和已知的坑。

## 测试决策

- 好的测试只看外部行为：给定输入文件或工作区，断言得到的工作区、警告、原因码或生成结果，不断言内部的辅助函数和中间结构。
- **预设合成（新接缝，主接缝）**：用测试内联的小样本文件，覆盖以下行为：
  - 同名数组拼接；
  - 按优先级、文件名排序并丢弃 `priority`；
  - 文案键替换；
  - 缺少文案键、键未被使用时的警告；
  - 悬空引用等校验问题以警告报出，并带条目 ID；
  - 语法错误带文件名和行列。

  真实预设也走这个接缝：测试读取预设目录中的实际文件交给合成函数，断言没有警告，并能通过导入校验。构建插件只是一层很薄的包装，不单独测试。

- **预设内容**：沿用现有预设测试中的语义检查（高危命令清单、每个 MCP Server 一条允许规则、标签引用有效、不含个人信息等）。新增一条：没有任何规则、又不在豁免名单（`dd`、`mkfs`、`chmod`、`chown`）中的命令工具，测试失败。
- **工作区文件**：导入带注释和尾随逗号的 JSONC；导出文件名为 `.jsonc`；规则带描述，导出后再导入保持不变；缺少描述的规则校验不通过；问题报告带条目 ID。参照现有的工作区文件测试。
- **工作区操作**：新增和修改规则时保存描述；合并预设时带上规则描述。参照现有的工作区操作测试和预设操作测试。
- **生成**：阶段二新增的每个 Agent 用快照锁定权限和 MCP 输出，确认规则描述不出现在输出中。参照现有预设测试中的生成快照。
- **Gist 客户端**：读写的文件名为 `agent-weave.jsonc`，内容按 JSONC 解析。参照现有的 Gist 测试。
- 界面部分（规则对话框和列表中的描述、导入框接受的扩展名、提示中的条目 ID）没有接缝，在浏览器中实际验证，并确认运行时只向 `api.github.com` 发出请求。

## 不在范围内

- 给预设文件提供 JSON Schema，用于编辑器补全和即时报错：先走通主流程，之后另做。
- 预设与界面的多语言：只提供简体中文，文案键只是为将来留下余地。
- 为不收录的 Agent 扩展 Agent 定义模型（如对象或数组结构的规则、TOML 策略、正则规则）。
- 兼容旧的工作区数据、旧的 Gist 文件名和缺少规则描述的旧文件。
- 输出沙箱、审批模式、工作区信任等权限之外的设置。
- Antigravity 远程 MCP 的 `url` 与 `serverUrl` 转换，以及 Codex 的 `env_vars` 改写：仍按约定原样输出，只在说明中提示。

## 补充说明

- 预设直接决定每位新用户的初始工作区。预设有逻辑问题时，用户刷新页面后本地数据会校验失败并回退到同样有问题的预设，修改随之丢失。因此逻辑问题虽然不中断构建，但必须在 CI 中拦住，部署前也要跑测试。
- 调研资料位于本地的 `docs.local/资料/` 下（Permission、MCP、Tools 三份），不提交到仓库。阶段二引用其中的事实时，应写进 Agent 格式文档，而不是只留在调研资料里。
- 拆分 Issue 时，规则描述的显示方式应复用工具列表中描述的现有呈现，不另做局部变体。
